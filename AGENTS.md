# AGENTS.md

This file is the flake standard for the `jgus-org` fleet: the rules every repository built on [flake-lib](README.md) follows, how to write one, and how to change the library itself. `CLAUDE.md` is a compatibility symlink to this file. It is addressed to whoever is working in a producer repository, which is usually a tree of `flake.nix`, `pin.nix`, `flake.lock`, and a document or two.

Read the surrounding tree before the rules; a published producer of the same shape is the closest precedent. Disagreement resolves in opposite directions by domain. This file is the source of truth for standards and procedures — what a producer owns, what an author writes, what the fleet does — so where a tree, an implementation, or another document disagrees with it about what should be done, this file rules and the disagreeing thing is what gets corrected. A producer that does it differently is drift, not precedent. An implementation is the source of truth for interfaces, so a library function's parameters live in the file that defines them, in `lib/` for the functions and in `templates/workflows/` for what a workflow installs, and neither this file nor the README restates them. Your own `flake.lock` names the revision of that library your flake actually runs, and that revision, not the current head of `v1`, is the one to read.

## Ownership

Everything rests on idiomatic Nix flakes. `flake.nix` declares symbolic dependencies and their intrinsic constraints; `flake.lock` resolves them to specific commits for one instantiation. Selecting another flake's `v1` rather than `v2` API is an intrinsic dependency and belongs in `flake.nix`; the commit currently selected from that branch belongs in `flake.lock`. Keeping both lets one specification build repeatably from its lock and receive logical continuous updates when it is re-pinned.

A `pin.nix` supplies lock-like state for resources that are not themselves flake inputs: the instantiated upstream version, source revision, fixed-output hashes, and dependency selections resolved for that upstream version. Standalone modules — flakes exposing their own modules, packages, or other outputs — need one only when they have comparable external state. Adapters — flakes that expose publicly available code or assets through idiomatic flake dependency management, carrying patches, extensions, and other modifications to the upstream offering where needed — always have one, and most of this fleet consists of adapters.

Ownership follows the reason for a value, not whether it contains a version number:

| Value                                                                                                      | Owner                                                        |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Supported API family such as `github:jgus-org/flake-lib/v1`, or an intentional compatibility constraint    | `flake.nix`                                                  |
| Concrete upstream revision, archive hash, or sibling ref resolved from one upstream release's requirements | `pin.nix`                                                    |
| Resolved commit for a declared flake input                                                                 | `flake.lock`                                                 |
| Generated dependency lists or other artifacts regenerated by that updater                                  | Committed alongside its pin, with version-specific ownership |

The bridge to a consumer is a committed producer tree: the consumer's `flake.lock` pins a producer Git commit, that commit contains `pin.nix` and its related artifacts, and those identify the exact external resources for the build. A moving input branch remains repeatable through its locked commit. Changing an upstream name or branch alone is insufficient where the instantiated pin or lock still selects something else.

The unit a producer versions is a unit versioned together, not a file count. One artifact might contain several files with an individual hash for each and a manifest, and a generated artifact set is reproducible with its producer's pin: the manifests and hashes that `update-version` regenerates belong to that pin's machinery, committed alongside it, rather than earning a producer flake for every file.

A `pin.nix` that mixes unrelated fields is a smell to act on: a pin holding an OCI image digest beside an overlay source revision covers more than one independently-versioned thing, and the fix is separate producer flakes that a consumer or adapter composes. Split along the version axis, not the directory. When an updater rewrites the whole pin for one concern — the OCI updater rewrites it to `{ imageDigest, imageHash }` — any field it would clobber confirms the conflation.

## Dependencies

All external dependencies come through an official, community, or fleet-owned flake. Nothing fetches an external source or asset directly. A dependency a community flake already supplies, including a nixpkgs package, needs no additional wrapper; every dependency or artifact that needs adaptation gets its own producer flake; wrappers compose separate input flakes rather than fetching unrelated upstreams together. A dependency is added to a flake for what that flake independently uses.

An input follows every input the parent already pins unless a specific technical reason blocks it. Following keeps the composed tree on one package set, which is the reason to compose through flakes at all; an edge that does not follow splits one instantiation into two that then disagree about the version of everything shared between them. The burden sits on the edge that drops the follow, and its reason must be technical and blocking and be written beside the edge. A formatter rendering identical text differently is not such a reason: a flake's formatter runs only in that flake's own root against that flake's own lock, so the version that root resolves is canonical for that tree whatever another tree resolves.

Consumption wiring belongs to the consumer. A producer carries no consumer's paths, defaults, or attribute names, and its README and all other prose address a public audience regardless of the repository's visibility. A patch that serves a consumer's need may live in the producer when it preserves existing defaults and other use cases and exposes a reusable option where behavior needs to differ.

## The producer README

Write it to whoever consumes the flake and never sees the repository it was authored in. Say what it is in the first line — a Nix flake that provides <thing>, with a link to upstream — then describe the artifacts it publishes and how to consume them.

Test every remaining paragraph against one question: does a consumer need this to use the flake correctly? If not, cut it. That rules out the update mechanism a scheduled workflow performs; how version branches and aggregate pointers are laid out; how the build works internally, including patches applied at build time and how hashes get acquired; and anything about the repository's history or why an approach changed.

What earns its place is what a consumer cannot read back off the outputs and would otherwise be surprised by: platform support, assumptions the package makes about its host at runtime, allowances that change what the consumer ships, and sharp edges such as an attribute whose contents land correctly only under a particular use. State these as facts about what you get, not as an explanation of the code that produces them.

## License and copyright

Every flake carries `LICENSE.md` at its repository root, and its `README.md` ends with a link to it and states nothing else about licensing. Where the flake carries or conveys someone else's code, `NOTICE.md` records that and the README's final line links it too. Each fact is stated once, in whichever of the two owns it; a README that restates either is a second copy that drifts.

`LICENSE.md` is the MIT grant over what we authored — the Nix, the scripts, the hooks, the documents, and the patches we authored — under `Copyright (c) <year> Joshua Gustafson`, dated the year the flake was authored, and nothing else. Reproduce the [canonical MIT text](https://opensource.org/license/mit) exactly, header and all, adding no line of our own — not even a link to `NOTICE.md`. A license file is detected by whole-file similarity, and the margin is narrow: measured with licensee over this exact grant, 1073 bytes is MIT at `Exact`/100.00%, and the same text with one 84-byte sentence appended is `NOASSERTION`. This repository's `LICENSE.md` is that 1073 bytes.

`NOTICE.md` is a heading and a table of the flake's **direct** dependencies and the notice each one provides — not a licence archaeology report. Its first row states what this flake authors and links `LICENSE.md`; every other row is one artifact the flake fetches, vendors, or conveys: the upstream source, a prebuilt binary, a model weight, a base image, a nixpkgs package it names. Each row gives the SPDX identifier and links the notice **that artifact provides** — its `LICENSE` at the pinned revision, or its canonical text where it ships none. Where nothing is linkable, one sentence naming its terms is the whole allowance for prose in a row. Quote upstream wording inline only where an upstream requires that wording to travel: Apache-2.0 §4(d) sends upstream `NOTICE` attributions along with derivative works, and the Qwen, Llama and Gemma terms require the agreement itself and a `Notice` holding a specific string. Where the obligation is discharged inside a built output rather than in this repository, the row says so and says where in the output it lands.

Stop at the direct dependency. A dependency's own dependencies are its record to keep: link what the artifact provides and let its notice speak for the rest. A table that walks a closure instead is not more accurate — it is a second inventory, wrong in ways the first one is not, and it is wronger every time the pin moves. Keep the columns narrow: prose a reader has to parse to find one licence is a formatting failure, and the same fact in two files is a copy that drifts, so `NOTICE.md` never restates the grant `LICENSE.md` gives or its scope.

The MIT grant does not reach a patch against an upstream whose own terms govern derivatives. A diff carries upstream source as its context lines, so a patch is plausibly a derivative of the code it modifies, and nixpkgs — which carries thousands — writes only that its MIT license "might not apply to patches included in Nixpkgs, which may be derivative works of the packages to which they apply." A patch against an MIT or Apache-2.0 upstream stays MIT, because both permit it under other terms; a patch against GPL, LGPL, or AGPL code travels under that upstream's license, which `NOTICE.md` states by naming it. Name every patch the tree carries, wherever it sits: a patch beside the module that applies it belongs to this inventory as much as one beside the directory that fetches the source, so inventory by searching for patches rather than by assuming only your own directory holds any. Where the tree holds nothing we authored to license — content that is entirely someone else's — there is no grant to write: ship no `LICENSE.md`, and let the README link `NOTICE.md` alone, which records the governing terms and grants nothing.

Naming upstream is not the same as carrying it. Every license above conditions itself on copies of the work, and Apache-2.0 defines a derivative work to exclude what "remain[s] separable from, or merely link[s] (or bind[s] by name) to the interfaces of, the Work", so an expression that pins upstream by URL, revision, and hash is our own work and nothing else — which is why nixpkgs itself is MIT. Shipping the built output is a different act: serving it from a binary cache or a registry conveys it, and a copyleft upstream then owes the recipient the corresponding source, which includes our patches. Say which of the two the flake does.

Write `NOTICE.md` only where there is something to record. A flake that authors everything its outputs carry writes no `NOTICE.md`, and writes no paragraph explaining that it has nothing to record: an assumed absence stated anyway is noise, and so is a sentence saying that some artifact is not this license's to give. What a `NOTICE.md` owes the reader is the distinction that changes who owes what, not a summary of what is absent. Our own code that reaches a repository by an indirect route — a workflow installed and refreshed from flake-lib's templates, a hook shared between flakes — is ours under the same grant and is not recorded there; flake-lib is this fleet's own library, and a file generated by it is authored here whatever directory it lands in.

No constructor, leaf flake, or publication step gates on a licence being declared: a check that can only see whether a field is populated certifies that and nothing about whether it is true. Whether the record is complete, and whether its terms are the ones the artifacts actually carry, is the half a reviewer reads.

## Authoring a producer

**Start from a close example.** Read one or two published producers of the same shape before writing, and read the shared library at the revision the new flake will use:

```bash
gh repo list jgus-org --limit 200 --json name --jq '.[].name | select(endswith("-flake"))'
gh api repos/jgus-org/<name>-flake/contents/<file> --jq .content | base64 -d
```

Declare flake-lib as an intrinsic input and carry the `follows` edge that [Dependencies](#dependencies) makes the default:

```nix
flake-lib.url = "github:jgus-org/flake-lib/v1";
flake-lib.inputs.nixpkgs.follows = "nixpkgs";
```

`v1` is the API family and the lock records its commit. A root that pins its nixpkgs under another name points the edge at that name — `jgus-org/nix` follows `nixpkgs-unstable` — and the edge, not the name, is the rule.

**A python producer is one `mkPythonFlake` call, whatever it publishes.** The leaf composes the payload, both updaters, the org formatter, the published family, and its checks from what the flake says it builds, so `flake.nix` carries the payload and nothing else. The arguments are in [`lib/mk-python-flake.nix`](lib/mk-python-flake.nix); neither this file nor the README restates them. A producer that runs its own `eachDefaultSystem`, binds `mkUpdateVersion`, `mkUpdateBranches`, and `mkFormatting` by hand, and appends to `pythonPackagesExtensions` itself re-derives four things the library owns — which is how two producers of the same kind end up shaped differently, and why the interface is one call with named arguments rather than a template to copy.

**Match the updater to what upstream publishes.** Where upstream publishes enumerable release names, add `update-branches` with its `pinSchema`. For upstream tracked by commit, `update-version` alone publishes a single branch whose commit log is the version history. A static module or devshell needs no updater. A flake carrying both `update-branches` and `update-version` is a branches producer — the orchestrator runs `update-version` per branch, so branches wins. Which source types have enumerable names is in [`lib/mk-update-version.nix`](lib/mk-update-version.nix): a `huggingface` pin, a `mutable-url` source, and any commit-tracked source have no enumerable names and take the single-branch workflow. For upstreams without versioned releases the updater synthesizes a dated version from the upstream commit date, so an unchanged upstream does not create an artificial new version each day; an unstable version label does not uniquely identify a commit, where `sourceRev` and the consumer's lock provide that precision. The tracking knobs `minimumTrackingVersion` and `trackStableOnly` are baked into the invoked package, which is their source of truth, so a workflow that only ever rewrites the file calling them cannot reset them.

**Expose the buildable package as `packages.default` when the flake materializes one.** A producer that publishes nothing buildable — a module or a bare source pin — needs no `default` and no updater, and is still gated, so a package or check added later is gated the day it lands. A producer built with `mkPythonFlake` publishes `default` itself when it has exactly one publishable payload attribute and binds none of this; a producer whose payload must resolve in the consumer's set is still a leaf, and [Overlay-published producers](#overlay-published-producers-and-cuda) holds that shape.

**Own every file the updater regenerates on its version branch.** `branchOwnedFiles` already covers the common set — the pin, the lock, and the generated artifacts a python producer's `update-version` rewrites — and `extraBranchOwnedFiles` adds the rest. Leave `flake.nix` unowned: a version branch inherits its specification from the base, and owning it would freeze an instantiated dependency choice.

**Configure no formatter.** `flake-lib.lib.mkFormatting { inherit self system; }` is the org program set — nixfmt with `pedantix` grouping, `ruff-format`, `shfmt`, `prettier`, `clang-format`, `gofmt` — together with the style files that constrain it, and both are flake-lib's in every repository: which formatter claims a file and what style it applies cannot vary between trees. The tools' versions resolve from the nixpkgs your flake-lib input resolves to, which your `follows` edge makes your own, so the version that formats a tree is the version that tree's lock names. A published flake therefore carries no `treefmt-nix` input and no copy of `.clang-format`. Bind it once in the per-system `let`, then `formatter = orgFormatting.formatter;` and `checks.formatting = orgFormatting.check;`. A producer built with `mkPythonFlake` publishes both from the leaf and binds neither: the binding is for a flake whose outputs the leaf does not compose. `excludes` is the producer's only formatter input, and upstream source the flake fetches at build time is not formatted, so name it there. Format before anything depends on the tree: the update workflow builds the package, never the tree, so nothing else catches drift, and a formatter sweep after consumers depend on the flake moves every line at once. The formatter and the update workflow do not fight — the updater writes Nix the formatter already accepts.

**Populate the hashes and verify.** Start the pin at the chosen version with empty fixed-output hashes, make new source files visible to Git-backed evaluation with scoped `git add -N`, and run the updater from the flake's own root, `nix run .#update-version`, passing an explicit version after `--` when needed. An artifact hook uses declared tools, is executable as a script, and emits the extra hash fields the updater expects; commit every file it generates. Verify the populated hashes, the package build, and the real consumer. Exercise hash machinery from an empty hash in a copy while keeping the populated pin in the tree. Repeat the updater when idempotency or artifact regeneration changed — unchanged-source paths can skip work, so inspect them before claiming everything refreshed.

## Pin shapes

The fields a pin carries follow from what identifies the artifact, and the updater rewrites exactly those. [`lib/pinned-source.nix`](lib/pinned-source.nix) names the source types and [`lib/mk-update-version.nix`](lib/mk-update-version.nix) what each resolves; `mkUpdateVersion`'s `buildTarget` names the single published package a build-failure hash is mined from, defaulting to the whole published family.

- **PyPI distribution** — `version` and `hash`. `source.pname` is the distribution's real name; the Nix attribute may differ. Source distributions by default, wheels only when upstream requires them and the builder supports the format.
- **GitHub or GitLab source** — `version`, `sourceRev`, `sourceHash`, fetched at the resolved commit. Release, tag, and commit discovery differ in capability.
- **One GitHub release asset** — `version` and `hash`, with `source.type = "github-release-asset"` and the matching `pinSchema`; the asset and tag templates resolve the URL and the hash verifies the content.
- **Generated vendor inputs** — the source fields plus `npmDepsHash`, `yarnHash`, or the field naming the generated input. Hook and hash strategy must match the actual generated input, and hashes may share `mkRevalidateHash`.
- **A toolchain version upstream's manifest constrains** — the source fields plus the selected nixpkgs toolchain attribute; the hook resolves the constraint at the new revision. No field when upstream constrains none.
- **One artifact of several jointly versioned files** — a version plus a custom keyed manifest, with a custom enumerator and `pinSchema = "version-only"`; the updater refills the whole manifest.
- **OCI registry image** — `imageDigest`, the manifest digest, and `imageHash`, the recursive Nix hash of the Skopeo directory, plus `version` when releases come from a GitHub tree, because the orchestrator names branches by version rather than by digest. `tag`, `os`, `arch`, and optional `variant` live in `source`, and the pinned platform is independent of the build host.

## Build toolchain versions

For any toolchain — compiler, interpreter, or SDK — use the nixpkgs default when upstream states no version requirement and that default builds the source. A selection nobody needed still costs: it changes derivation identity even when the built content is byte-identical, and it drifts above or below what upstream develops against without anyone choosing it. Where upstream does constrain a toolchain version, route the constraint through the pin instead of a literal in the derivation: the artifact hook reads upstream's own expression of it at the resolved revision, writes it into `pin.nix`, and `flake.nix` selects the nixpkgs attribute the pin names, so a version bump refreshes the selection. `extraHashes` declares the pin fields the hook refills and is not limited to hashes. A constraint we hold that upstream does not state — an intentional compatibility pin — is specification and belongs in `flake.nix`.

The discriminator is enforcement, not the presence of a version file. A directive the tool itself refuses to build without is a constraint; a version file nothing consults during the build is upstream's development environment, and adopting it makes our choice look authored by whoever last edited upstream. Constraints are expressed by `go.mod`'s `go` directive, `engines` in `package.json` or a `.nvmrc`, `requires-python` in `pyproject.toml`, and `rust-version` or `rust-toolchain.toml`.

When upstream states nothing binding, write no selection at all: the derivation takes `bun` and `nodejs` from the top-level attributes, so an explicit version argument only restates the default. Confirm the default clears any floor the tree declares first — a floor it fails has moved the tool into the constrained case. A floor the default clears leaves the tool unconstrained however firmly the manifest states it: an adapter whose `go.mod` declares `go 1.26` against a nixpkgs default of `1.26.8` writes no Go selection. Where the floor is above the default, record the attribute that satisfies it in `pin.nix` and let the pin drive the selection:

```nix
goPackage = "go_1_27";
```

```nix
<producer> = (pkgs.buildGoModule.override { go = pkgs.${pin.goPackage}; }) { … };
```

Derive the attribute from the module's `go` directive, ignoring any `toolchain` line, in the hook the updater runs with `NEW_REV`, `GH_OWNER`, and `GH_REPO`; inside a Nix indented string each shell expansion is written `''${…}`. Go's floor is never advisory: `buildGoModule` sets `GOTOOLCHAIN = "local"`, so a module whose `go` directive exceeds nixpkgs' `go` fails instead of fetching a newer compiler. Where the floor is above the default, prefer the pin-driven form over a versioned alias such as `buildGo127Module`: the alias is that same builder with the override already applied, so each produces an identical derivation, and only the pin can be refreshed by the updater. A selection naming an attribute this nixpkgs lacks fails evaluation by name; that is the signal to raise the nixpkgs input, never a reason to fall back to a default silently.

## Python payloads and overlays

**A python application's dependency _versions_ belong to the interpreter package set that builds it, not to its producer.** An adapter names the packages the application needs and lets that set choose their releases. Vendoring wheels, committing a resolved dependency lock, or overriding one package's version is a deviation that needs a named gap — a dependency the set does not carry, or a version floor the application requires and the set does not meet — stated in the specification that declares the deviation, where an updater cannot rewrite it. Without that gap the lock is the producer re-solving a problem the package set already owns, and every bump of it is maintenance the fleet pays for nothing. A dependency the set carries is not a gap, and a compiled extension the set builds against the deployment's own CUDA configuration is the opposite of a gap: the wheel of that extension is the weaker artifact, because it cannot be rebuilt against anything the consumer configures. A producer that used to vendor what its consumer's set already carries deletes the locks, the manifests, and the wheel-install machinery along with the reason.

**Where the recipe lives follows the published interface, not the length of the expression.** The payload function is called with the set its payload lands in — `pkgs` for the outer set, `python` for the interpreter's set as it arrives after every earlier overlay and extension, and `src` and `version` for the fetch the pin names wherever `upstream` is given. A recipe names members of `python` the way its own `buildInputs` resolve, and never picks a python package out of an outer set by hand. `buildPackage` and `buildApplication` are `buildPythonPackage` and `buildPythonApplication` against the pinned source with this fleet's defaults: `doCheck` off, and a recipe that says nothing about how it builds gets `pyproject = true` with setuptools. Where a build or check input is not a python package — a D-Bus broker the suite talks to, a tool it shells out to — name it in the recipe beside them.

An application producer — the thing it builds is the application — publishes its payload through `payload.packages`, written inline in `flake.nix`, because that recipe _is_ the flake's statement of what the application needs; splitting it into a satellite file separates the statement from the flake that makes it. A producer that instead bumps one nixpkgs attribute past a floor publishes through `payload.overlays`, and its delta lives there, where a reviewer reads it against the recipe the consumer's set already carries. A producer that does both states both in one flake.

**Bump because the set cannot meet a floor, not because upstream's resolver chose elsewhere.** Where nixpkgs meets every declared range, the application builds against nixpkgs unmodified and the producer bumps nothing. State the unmet floor and the version nixpkgs carries at the declaration that applies the bump — `flake.nix`, which no updater owns; a `pin.nix` is rewritten wholesale at each bump and keeps no reason. The floor is a claim about the consumer's set, so measure it there: evaluate that set for the attribute's version and its `meta.broken` rather than reading a changelog.

Bump an existing nixpkgs python package by appending to `pythonPackagesExtensions`, which `payload.overlays` does for the producer, and compose multiple extension overlays with `lib.composeManyExtensions`. Never use an outer `python3.override { packageOverrides = …; }`, which can leave the interpreter's self-referenced `python.pkgs` on the old version while `pkgs.python3.pkgs` shows the new one — compare through the consumer and inspect its runtime closure.

**State the delta over the consumer's own recipe.** Where the consumer's set already builds the attribute and only its release moves, override that recipe and carry what the new release changes: the source the pin names, a dependency the new release declares that the channel's recipe does not, the test selection a new layout needs, the floor that flips `meta.broken`. The recipe stays the channel's, so a bump re-adapts a delta instead of re-copying a recipe, and the difference this producer makes is an expression rather than a description of one. The producer does take the shape of a recipe it does not own, and a delta is complete only by assertion, so measure it: build the package both ways and compare the derivations' member sets, since every store path that appears on one side and not the other is a dependency the delta missed. A delta that restates only what the release _moved_ drops a dependency the release _added_, which no reading of the expression shows.

**Where a recipe is a nixpkgs recipe copied rather than written here, record the base and the diff in `PROVENANCE.md` at the producer root.** One row per recipe: the nixpkgs revision and path it came from, the command that reproduces the base file, the attributes that differ and what makes each difference safe, and the condition that retires the copy. `pin.nix` is rewritten wholesale at each bump and the recipe moves under the new version, so neither can carry this, and without it the next maintainer cannot tell a deliberate deletion from an oversight. An override of the consumer's own recipe needs no such row: the override is the diff, and each field that differs states its own reason.

**Run an upstream suite only where the suite is the verification.** `doCheck = false` is the default for packaged upstreams: the upstream ran its own suite, suites are not free, and a resource-hungry suite times out on a loaded builder and reports a build break that is not one. Opt in per recipe where the thing under test is the closure this flake moved — a bumped dependency floor, patched tests — and record which in the `PROVENANCE.md` row, or beside the `doCheck` where the producer keeps no `PROVENANCE.md`.

## Overlay-published producers and CUDA

**Resolve the payload in the consumer's set when the deployment owns part of it.** `payload.overlays` is where such a payload is stated, and the leaf publishes the same attributes in `packages.<system>` beside it. Two shapes reach this. A CUDA-using producer does because the deployment owns the CUDA configuration. A producer of an artifact nixpkgs marks unfree does because nixpkgs refuses to instantiate it in any set that has not said otherwise, so the build — and the answer for the licence — belongs to whoever performs it.

**Consume the overlay, not the published attribute.** The published family is the payload built at this flake's own nixpkgs and its own configuration, so it differs quietly from what the overlay deploys, and whoever builds it gets an artifact no host runs. The deployment interface stays `overlays.default`; `packages` is the surface the gate and the updater address.

**Name what the check needs in `gate.config`.** A payload that cannot be instantiated at the producer's own configuration — an unfree one is not even instantiated, which is the point of unfree packaging — would otherwise ship a branch that cannot build at all, so the leaf builds the published family a second time in a tree carrying exactly the configuration the payload cannot ask for itself:

```nix
gate.config = {
 allowUnfree = true;
 cudaSupport = true;
};
```

The grant inside the check is not an acceptance on a consumer's behalf: the same overlay applied to a set that permits nothing unfree is refused exactly as before. The published attribute stays config-free, which is what keeps the overlay portable to whatever set consumes it.

**State a CUDA payload in `payload.packages`.** The leaf calls the payload with the set that resolves it, so every part of it — the torch environment, the app tree, the launcher — defers to the consumer, and the deployment interface stays `overlays.default`. CUDA configuration belongs to the set that builds torch because `cudaSupport`, `cudaPackages`, and `cudaCapabilities` have exactly one correct value — the one the host's GPU and driver have — and no producer can see it. An overlay defers every reference to the consumer's package set, so identical producer source builds torch against whatever CUDA the deployment carries, the same way every other GPU workload here gets CUDA. A flake that builds torch at its own flake scope instead instantiates its own CUDA configuration at its own nixpkgs revision, and its torch no longer shares `cudaPackages` with anything else in the image; the disagreement surfaces as a CUDA-major mismatch between the app's torch and a natively built backend's `libggml-cuda.so`. Composing GPU producers as overlays on one package set is what keeps them on a single `cudaPackages`.

**Take CUDA from the set, never from the pin.** `torch`, `torchvision`, `torchaudio`, `triton`, and the `nvidia-*` and `cuda-toolkit` distributions they pull belong to the deployment's `cudaPackages`, so a CUDA-using producer's pin carries no CUDA field; a vendored `torch` would pin against a driver the producer cannot see. The runtime is then one interpreter built from that set, with the app tree beside it rather than in front of it. `autoPatchelfIgnoreMissingDeps` names a GPU-extension dependency on a runtime the deployment never provides — a ROCm `libamdhip64.so.7` shipped beside a CUDA extension — where the patchelf rewrite is not what makes the extension loadable.

## Depending on an unmerged change in another repository

A change sometimes spans two repositories, where work here depends on a branch of another before either is committed. `flake.nix` names the API family, never a branch: editing the input's URL to point at a branch does work, but it makes an easy-to-forget cleanup step that bites more often than it's worth, and the API family named in `flake.nix` is specification, so a temporary affordance must not survive into a merged tree. Put the branch in the lock instead:

```bash
nix flake lock --override-input flake-lib 'github:jgus-org/flake-lib/<branch>'
```

This edits _only_ `flake.lock`. It is stable for iterative development as long as you don't re-lock it, safe to check in — it works as expected for anyone who pulls it — and the next flake re-lock does the right thing, so there is no revert step to forget. The same form covers any other input, and it is how a consumer-side draft is verified against a flake-lib change that has merged but not yet reached the `v1` head. It is your responsibility to keep flake locks up to date when working with interdependent pull requests.

## Build verification

`nix run github:jgus-org/flake-lib/v1#build-and-check` is what a tree has to pass: it builds the packages the flake publishes for the runner's system and runs `nix flake check --no-write-lock-file`, which builds the checks. Every step runs even when an earlier one fails, so one run names every problem in a tree rather than the first nix reached. The publication path runs the same command, so a refreshed version branch is published on the evidence a pull request would have produced, and a push made with `GITHUB_TOKEN` triggers no further workflow. Neither half names the attribute it builds, so a producer publishes exactly what a pull request would have gated. README's gate section owns the rest.

The gate is template-owned, and promotion installs the refresh beside it for every producer — the one whose updater is `none` too, which is the case that refresh exists for. An installed workflow is not a frozen copy: `nix run github:jgus-org/flake-lib/v1#update-workflows` advances the flake-lib input on a schedule of its own and rewrites every workflow that revision has a template for, in one commit, so a workflow and the scripts it invokes move together. Nothing producer-specific lives in the workflow for that rewrite to lose — the per-producer knobs are `flake.nix` constructor arguments baked into the invoked package — so a template replaces its workflow file wholesale, and a refreshed file takes effect for the next run of the workflow it rewrote, never the run whose commit wrote it. What a producer can configure about its gate is `passthru.ciBuildSkip` on a package, the `RUNNER` repository variable, and the repository's secrets. What a bespoke workflow verified that the template does not belongs in `checks`.

There are two skips and each needs its reason written beside it. `passthru.ciBuildSkip` excuses one package from the gate's build half, and every run prints the names it excused so an exemption cannot go unnoticed; `buildVerificationSkip` excuses a refreshed version branch from the publication gate whole. Before using either, ask whether the proposed reason is really a sign that we are doing the wrong thing in a build. A build might have a legitimate need to run a VM or require special hardware, but probably not — a `nixosTest` suite usually earns its gate on the driver derivation, which builds every guest and boots nothing. The one legitimate excuse encountered so far is resource constraints on free GitHub runners: a very large build can legitimately require a nix closure larger than will fit on such a machine. A flake that locks a private repository needs `BUILD_TOKEN` on that repository; `ATTIC_TOKEN` and `ORG_UPDATE_TOKEN` are fleet-level and a producer declares nothing for them.

## Changing flake-lib

flake-lib owns reusable source discovery, pin updates, hash acquisition, dependency cascades, artifact hooks, and version orchestration, together with the workflow templates and the cache action it publishes for producers. Compare a producer's source, hash, build, and publication needs with its current capabilities before implementing them. Reuse a matching strategy; extend the library for a reusable gap within the authorized task; keep package-specific builds and genuinely unique artifact transformations in the adapter, and explain any machinery kept bespoke and what would warrant generalizing it.

Land a change here with its tests, its README section, and the example package or check that exercises it. The library installs the same gate for its own pull requests that it ships to producers, so that run is the evidence a body points at, alongside the local verification: `nix flake check --option abort-on-warn true`, or the named `checks.<system>.*` builds that ran.

Keep the change additive inside the API family the fleet consumes. `v1` does not move an interface out from under its consumers, which is why an advance to `v1` flows through producer lock updates without re-auditing an adapter's existing API usage; a change that does move one is a `v2`, and every consumer takes that migration deliberately, so one push cannot break every repository at once.

Merges land on `main`; the maintainer cuts the `vX.Y.Z` tag and advances the `v1` branch, and a consumer receives the change when `nix flake update flake-lib` reaches the new head. Later stages wait for that advance instead of landing against it, and cutting tags, advancing `v1`, merging, and deploying all belong to the user. Where the change is visible in how a consumer composes the library, demonstrate the new interface in one to three draft pull requests on producers whose shapes differ: the library's own examples do not exercise an adapter's shape, and a draft is the cheapest evidence the interface fits a real consumer. Omit the drafts when the change is internal to the library. Where a new flake-lib tool and a workflow template naming it arrive together, the tool reaches `v1` first — a template naming something `v1` does not publish fails every installed gate at once, while the tree introducing both passes its own in-tree check, which reads tool names against what that tree publishes.

## Changing a standard the fleet follows

A standard is a rule every producer follows: the ownership split above, the authoring rules, and the formatter, build-host, and updater conventions producers repeat. Changing one changes every repository the rule reaches, so the change is the rule plus its applications — a rule merged without its fleet leaves two conventions and no record of which one a new producer should copy. The agent's part is documentation and pull requests.

Land the rule before applying it. Write the standard where guidance of its kind lives, before editing any repository: this file for what a producer owns and why and what an author writes, [README.md](README.md) for how a producer composes the library's interface, the implementation's own leading doc comment where the interface itself changed. One directive has one source of truth. Where another file needs it, that file links the file that owns it instead of restating it, so the directive changes in one place and nothing has to be kept in step; where changing a rule turns up the rule copied elsewhere, delete the copy and leave the pointer. Two copies of a directive are two rules, and which one the next author follows is decided by whichever file they open first. Prefer enforcement to prose where the rule is derivable: a flake-lib `checks.<system>.*` test can assert library behaviour, `checks.formatting` can fail a commit on drift, the publication gate can refuse a tree. Nothing in this fleet audits the producer standard against the live tree on its own, so a rule with no check holds only until the next audit; name the check that owns the rule in the rule itself.

State a conditional rule by its discriminator, not by its current exceptions: "a producer that publishes nothing buildable needs no `packages.default`" lets an author decide about a flake that does not exist yet, and a list of exemptions does not. Keep the audience in mind — the reader is the agent that comes after you, adding or changing one flake, and it needs to know how to use what it needs, not how every piece of it is implemented. Do not write a protocol for migrating existing code into the standard: the migration is your job, and once it lands no agent after you will ever need to do it again. Never write instruction just for the sake of checking a box here; if a small note in one file fills the need, then do just that.

Apply the rule per target. Three targets, each with its own discriminator, and a change reaches any subset of them:

- **flake-lib**, when the implementation belongs to shared machinery — the capabilities above that the library owns — or to the workflow templates and cache action it publishes for producers.
- **the fleet's monorepo root**, always: the root is itself a producer, and it is where the rule reaches the consuming side the library cannot, together with the local producers it holds.
- **Published producers**, every active `jgus-org/*-flake`, audited one at a time — a rule scoped by shape reaches some producers and not others, so the fleet is not changed as a unit.

Enumerate the fleet and exclude retired producers — an archived repository is one the fleet stopped maintaining, and a pull request there claims otherwise:

```bash
gh repo list jgus-org --limit 500 --json name,isArchived \
 --jq '.[] | select((.name | endswith("-flake")) and (.isArchived | not)) | .name'
```

Audit each against the rule as written, reading the files the rule reaches from GitHub:

```bash
gh api "repos/jgus-org/<repo>/contents/<path>" --jq .content | base64 -d
```

or cloning into task-scoped storage when it reaches the whole tree. Match the rule's expression rather than one spelling of it; the fleet writes `formatting = treefmtEval.config.build.check self;` as readily as `checks.formatting = …`, so a literal search under-reports.

Choose the fan-out by how many repositories the rule reaches. Fewer than about five or six: open one pull request per repository now, since the fleet converges in one review cycle and every diff stays small enough to read. More: pick about three repositories whose shapes differ — a branches producer, a commit-tracked single-branch producer, a module or overlay publishing nothing buildable, an OCI image producer — open those, and stop for the user's approval of the pattern before the remainder. A wrong pattern is multiplied by the count that was skipped, and each producer's scheduled updater keeps committing underneath an open pull request.

A producer's pull request carries every standard change that reaches its tree, not one pull request per standard. Where the rule lands in a flake-lib workflow template, check that the producer's installed workflow is template-owned before leaving it alone: the refresh rewrites only the files the advanced revision has a template for.

Verify inside the producer's own tree — `nix flake check --option abort-on-warn true` and the gate its workflow runs. Title the pull request as a sentence naming the behavior, and put the commands you ran and their counts in a `## Verification` section. Where the flake publishes through an overlay, the tree's own declaration is what builds the payload, so name that build in the section; where the claim is about the composed set — a CUDA backend resolving against a consumer's `cudaPackages`, an overlay applied to a package set this flake does not lock — the section names the consumer measurement that showed the change works, because no build inside the producer's tree can show that. Report the pull requests opened and the pattern awaiting approval; merge nothing.
